SAPNDA

Unifying Admin Settings across products in Business Data Cloud

Business Data Cloud brings together SAP Analytics Cloud (SAC), Datasphere (DSP), and BDC under one platform. Differences in how admin settings were structured across products created a noticeable inconsistency for administrators. Collaborating with one other UX designer, I worked across two connected workstreams: one focused on compliance for browser integration and tenant appearance, and one focused on establishing a shared layout standard for admin settings across all products. This project is under NDA, so details shared here are intentionally high-level.

Platform Figma
Tasks Cross-platform Alignment
Timeline 6 months
Role UX Designer

context

A platform bringing multiple products under one roof. The admin experience needed to follow.

SAP's Business Data Cloud brings together multiple products under a single platform. Each product had its own administration area, built independently over time. Datasphere was built after Analytics Cloud and reused its components to ship quickly, and different teams owned different sections of the settings. The result was settings that looked and behaved differently between products, with some options, like security settings, appearing in more than one place.

As the UX Designer on this project, I was embedded within a cross-functional team working across UX, development, user assistance, and product management, with team members distributed across multiple countries and product areas.

problem

Inconsistent admin experiences across products, addressed in parallel.

Administrators working across multiple products encountered different layouts, interaction patterns, and settings structures depending on which product they were in. Some settings also fell short of SAP's internal UX consistency standards: Datasphere showed its own icon as the browser tab icon instead of SAP's, and both products used hard-coded custom colors instead of themeable design tokens.

Two related problems were scoped together and run as parallel workstreams, allowing shared learnings to feed into both without duplicating effort.

goals

Align structure, standardize components, and give every admin tab the same foundation.

The goal across both workstreams was consistency: bringing admin settings across products into alignment so administrators experienced a single, predictable interface regardless of which product they were in. This meant meeting the consistency standards, establishing shared layout standards, unifying interaction patterns, and producing one set of specs detailed enough for development teams across multiple countries to implement independently.

process

Auditing the current state

Both workstreams started with an audit of the existing experience, mapping inconsistencies across products and identifying what a unified standard would need to cover. The audit surfaced a range of issues that had accumulated over time as each product built its admin area independently.

Workstream 1: browser integration and appearance, in three scopes

System information bar. The bar that tells users which system they're in used hard-coded hex colors. I moved it to design tokens so it follows the theme. The component itself is covered in the DNA Web UI Kit case study.

Browser tab icon. SAP's icon became the default, with a custom option kept for customers who want their own. To avoid surprising anyone, I planned a rollout where existing customers keep their current icon and new customers start with the SAP default. I also designed for an edge case: a light-themed app open in a dark-mode browser, where the icon still needs to be visible.

Settings layout. I explored several layouts for the appearance settings and we chose an object page floorplan. I also moved the "Default Appearance" settings so both products keep them in the same place.

Workstream 2: unifying every admin tab

The new floorplan then became the standard for every admin tab across Analytics Cloud, Datasphere, and Business Data Cloud, so admins don't need to relearn each tab. We phased it: admin settings first, then configuration settings and a search across tabs. I wrote guidelines for text and input field lengths and turned the layout into a page template for the DNA Web UI Kit, so future tabs start consistent.

One decision came up repeatedly: toggles versus checkboxes. Toggles suggest a change saves instantly, but the new layout uses save and cancel buttons, so I switched those settings to checkboxes.

Designing and iterating

Design proposals were reviewed iteratively with the UXC lead, senior designer, and development lead. With the user assistance team, I refined labels so each one said what it does. Feedback also shaped the format of the specs, which were structured to be navigable by development teams without requiring them to work through the design file directly.

Working across teams

Both workstreams involved coordinating across UX, user assistance, project management, and development. Scope changes mid-project were incorporated without restarting the work, and regular check-ins ensured the direction remained feasible across all product areas involved.

outcome

Both specs completed, handed off to development, and unified 20 tabs across 3 products.

Both specs were completed and handed off to development. The settings now meet the consistency standards, the system information bar uses design tokens, and the floorplan and guidelines live in the DNA Web UI Kit for future tabs. Full case study details are available on request.

reflections

Decisions take time, and that's okay

Even small design decisions can involve multiple stakeholders, reviews, and back-and-forths before a direction is locked. Working at enterprise scale taught me to separate the design work from the decision-making process. Keeping specs well-documented meant that when decisions finally landed, implementation could move quickly.

How you present work matters as much as the work itself

I learned early on that the format you use to present to developers shapes how well they understand the design intent. A Figma file works in a design review, but a structured spec or a live prototype is what actually moves things forward in a dev handoff. Developers respond well to being able to interact with the design directly rather than interpreting static screens. Finding the right format for the right audience became a skill in itself.

A spec should work without you in the room

Early feedback was to build each spec so that anyone opening it cold would have enough context to understand it without me presenting. That changed how I wrote them: context first, then the decision, then the details, in the order a developer would need them.

Leading design conversations and advocating for decisions

Working with developers and project managers on a regular basis gave me hands-on experience presenting design rationale and defending decisions in a professional setting. One thing I underestimated early on was assuming stakeholders remembered the full context of the project. In reality, everyone is juggling multiple workstreams, and coming into a review with full context, not just the latest changes, made conversations more productive and helped move decisions forward faster.
